## Problem Statement

Engineers learning AI/ML know the feeling: you finish a tutorial, feel like you understood it,
then sit down to build something and realize you understood nothing. Existing tools either
tell you answers (passive) or give you projects (aimless). Nobody connects the moment of
"I think I get it" to a proof that you actually do.

DeepPath's core loop: open-ended Socratic grill session on this week's curriculum topic →
at the end, a specific project that proves the exact gaps that surfaced.

## What Makes This Unique

Every Socratic tutor ends with "great job, you understand it." Every project platform says
"here's a project." Nobody ends the tutoring session by assigning the specific project that
*proves* understanding of the gaps that surfaced in that conversation.

The product is **proof**. Not tutoring. Not projects. The closed loop between "I think I
understand" and "here is evidence I do."

## Constraints

- Building for yourself first — daily personal use before showing anyone
- Codebase already has: Next.js App Router, Claude streaming, adaptive curriculum generation, onboarding
- Side project pacing — needs to be usable within 1-2 days, not 2 weeks
- Session should feel open-ended, not timer-based — ends when you say "I think I get it"

## Premises

1. The session is open-ended — ends when the user signals readiness, not on a timer. AGREED.
2. The project assignment is generated FROM the conversation gaps, not a pre-set list. AGREED.
3. The AI needs curriculum week context to be useful — without it, it's a generic chatbot. AGREED.
4. (From second opinion) The project should come with verifiable acceptance criteria tied to
   specific gaps — not a vague idea. AGREED (strengthens premise 2).

## Approaches Considered

### Approach A: Chat page + gap extraction (CHOSEN)
- Summary: Build the Socratic chat UI wired to Claude with curriculum context. At session end,
  extract gaps and generate a project assignment. Simple prompt engineering, no structured data layer yet.
- Effort: S (2-3 days — streaming chat + separate non-streaming close-session call)
- Risk: Low
- Pros: Ships fast; concept validated before architecture decisions; separate close-session call avoids stream parsing complexity
- Cons: Gap model lives in the prompt and the close-session response — no persistent GapModel entity yet, harder to aggregate across sessions
- Reuses: Existing auth session handling, plan API for curriculum week data, `projects` table insert pattern

### Approach B: Stateful GapModel + ProjectSpec with acceptance criteria
- Summary: Structured pipeline — socratic-session outputs `GapModel`, project-compiler outputs
  `ProjectSpec` with `acceptance_criteria[]`.
- Effort: M (3-5 days)
- Risk: Med — spend days building before knowing if the concept clicks
- Pros: Every session improves the extractor; proof is concrete and verifiable
- Cons: Over-engineered for a concept that hasn't been validated yet

### Approach C: Session → failing test suite
- Summary: Session ends with runnable tests that probe your specific gaps. Make them pass = proved understanding.
- Effort: L
- Risk: High — generating runnable ML test code is genuinely hard
- Pros: 100% objective proof; uniquely memorable
- Cons: The test IS often the project; UX friction may kill daily use

## Recommended Approach

**Approach A** — build the chat page and gap extraction first.

Rationale: The codebase already has Claude streaming working. The fastest path to knowing
whether the concept feels right is to use it on yourself. Once the loop feels good, evolving
to Approach B (structured GapModel) is a clean upgrade, not a rewrite — you'll just be
adding a second Claude pass that extracts structure from the conversation transcript.

## Implementation Notes (Approach A)

**Auth:** All tutor routes require authenticated user (existing session cookie). `userId` is
extracted server-side from the session — never passed from the client. The curriculum week
selector fetches `/api/plan?userId=<from-session>` to get the user's current plan.

**Conversation persistence:** Client-side only (`useState` or `sessionStorage`). An explicit
accepted limitation — refreshing the page loses the session. This is fine for personal daily
use. Upgrade to DB storage only if needed after validation.

**Files to create/modify:**
- `app/(dashboard)/tutor/page.tsx` — chat UI, curriculum week selector (fetches from
  existing plan API), conversation history in local state, "End session" button
- `app/api/tutor/chat/route.ts` — streaming endpoint, input: `{ weekTopic: string,
  conversationHistory: { role: 'user'|'assistant', content: string }[] }`, auth required
- `app/api/tutor/close-session/route.ts` — non-streaming, input: `{ weekTopic: string,
  conversationHistory: Message[] }`, runs ONE Claude call (gap extraction + project
  generation bundled), saves result to `projects` table, returns
  `{ projectId: string, gaps: Gap[], projectAssignment: ProjectAssignment }`

**Session end mechanism — one pattern only:**
The user clicks "End session" button. No client-side phrase detection — one trigger only.
The frontend calls `/api/tutor/close-session` with the full conversation history (max 50 turns
enforced server-side to prevent oversized payloads; trim oldest turns if exceeded).
Claude does NOT output JSON mid-stream during the chat — the chat stream is plain prose only.
The gap extraction + project generation happens in a separate, dedicated close-session call.
This avoids stream parsing complexity and guarantees the JSON comes from a controlled call.

**Chat system prompt:**
```
You are a rigorous mentor tutoring an engineer on: {weekTopic}.
Context: They are on Week {weekNumber} of their AI/ML learning path.
Previously completed: {completedTopics}.

Rules:
- Ask ONE question at a time. Never give explanations or answers unprompted.
- Start with a foundational question on {weekTopic}.
- When they answer correctly, probe deeper or adjacent.
- When they fumble, ask a clarifying question that exposes the gap — never fill it in.
- Keep responses short (1-3 sentences max).
- Never say "great answer" or give praise — just probe further.
- Continue until the user ends the session.
```

**Close-session Claude call — single bundled call:**
```
System: You are analyzing a Socratic tutoring transcript.

Given this conversation on {weekTopic}, output JSON only (no prose):
{
  "gaps": [{ "concept": string, "severity": "low|med|high", "evidence": string }],
  "projectAssignment": {
    "title": string,
    "description": string,
    "acceptance_criteria": string[]
  }
}

Rules:
- Maximum 2 gaps (highest severity only)
- Project MUST be derived from the gaps, not generic to the topic
- Acceptance criteria are checkable by running code or inspecting output —
  e.g. "loss curve shows degradation when X is removed", not "understands X"
- If gaps are too scattered, pick the one gap with the most fumbled turns
```

**Project assignment storage:** Saved to the `projects` table as status `'planning'`,
linked to `curriculum_week`. This is a committed decision. It does NOT automatically
appear in the existing plan UI yet — the plan UI wiring (step 4 in Next Steps) is
explicitly deferred until after the core loop is validated. The row exists in the DB;
it just isn't surfaced in the UI until step 4 is done.

**Error handling for close-session:** Wrap the Claude call in `try/catch`. On error or
malformed JSON parse failure, return `500` with `{ error: "Session summary failed" }` and
show an inline error in the UI: "Couldn't generate your project — try ending the session
again." Do not save a partial result to the projects table.

**The proof sentence format:**
> "Here's your project: [title]. [1-sentence description].
> Your proof: [specific, runnable/checkable acceptance criterion from a gap]."

**Verifiable** means: the user can check it by running code, inspecting output, or
measuring a concrete value — not by asking "do I understand this?"
