## Problem Statement

Busy engineers trying to reach frontier labs (Anthropic, OpenAI, DeepMind) are stuck in a doom loop: passive content consumption (newsletters, YouTube, papers) never produces proof of understanding. AI tutoring tools (ChatGPT, Claude) are unstructured. Courses are expensive, boring, and don't fit into a workday. The core pain is not lack of content — it's that the field moves faster than any learner can sequence, and nothing converts learning into career-legible evidence.

## Target User

A mid-level software engineer, currently employed full-time, who:
- Wants a job at a frontier AI lab specifically (not just "learn AI")
- Can only consume content during work hours in 5–10 min bursts
- Builds in the evenings
- Has finished at least one structured AI course but feels stuck between "knows the theory" and "can prove it"
- Is active on LinkedIn and wants a public trail of their AI work

**This user is the founder.**

## The Wedge: Proof Trail

Every Socratic session ends with:
1. A GitHub-ready micro-project (spec + acceptance criteria — already generated by close-session)
2. A LinkedIn post draft: "I learned X, here's what I built to prove it"
3. A one-sentence proof line: concrete, runnable, checkable

**Zero direct competitors.** Every existing tool (The Rundown, TLDR AI, 100.school, The Batch, workatafrontierlab.com) optimizes for consumption metrics. None produce proof. The gap between "consumed content" and "career-legible artifact" is completely unoccupied.

## Status Quo

The doom loop:
1. Passive consumption — newsletters, YouTube, papers. Never applied.
2. ChatGPT tutoring sessions — unstructured, no follow-through, nothing to show.
3. Started courses — abandoned when real work gets busy.

## Constraints

- Solo founder, building in evenings
- Socratic tutor already shipped and working (80% of the proof trail is done)
- No external users yet — personal use case first
- Content curation at scale requires a crawler (deferred)

## Validation Gate (before any build)

Do 3 Socratic sessions manually. After each one, hand-write the LinkedIn post using the proof line from close-session. Post to LinkedIn. Only proceed to build if:
- 3 posts published within 2 weeks
- At least 2 get engagement from AI practitioners (comments or connections from people you don't know)

**Contingency:** If the gate isn't met within 2 weeks, revisit the post format. Read 10 examples from researchers who got hired at frontier labs. Revise the prompt spec in Build Step 1. The gate is a quality signal, not a kill switch.

## Build Step 1: LinkedIn Post Generator (~2h)

**New API route:** `POST /api/tutor/generate-post`

**Inputs:** `{ weekTopic, gaps[{concept, severity, evidence}], projectAssignment: {title, description, acceptance_criteria[]} }`

**Output:** `{ postDraft: string, proofLine: string }`

**Model:** TUTOR_MODEL + AbortController 8s timeout

**Prompt intent:** "Write a LinkedIn post (150–200 words) for an AI engineer who just learned [topic]. They identified these gaps: [gaps]. They're building this project to prove it: [title + description]. Their proof line is: [acceptance_criteria[0]]. Tone: practitioner-to-practitioner, not humble-brag. Lead with the specific thing they learned, not 'I explored.' End with the proof line and a note that the project is on GitHub."

**UX:**
- Loading: "Generating your LinkedIn post..." skeleton
- Success: editable `<textarea>` with post draft
- Two copy buttons: "Copy proof line" | "Copy full post"
- Fallback on timeout: "Couldn't generate post — here's your proof line: [proof_line]"
- Trigger: generate-post fires sequentially after close-session returns 200 in TutorChat

**Technical acceptance criterion:** Post draft appears within 5s (p95), 8s hard timeout with fallback, textarea editable, both copy buttons present.

## Build Step 2: Proof History Page (~4h)

**Route:** `/proof`

**Schema additions (new table — not ALTER):**
```sql
CREATE TABLE tutor_sessions (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id             uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  session_date        timestamptz NOT NULL DEFAULT now(),
  week_topic          text NOT NULL,
  gaps                jsonb NOT NULL DEFAULT '[]',
  project_title       text,
  project_desc        text,
  acceptance_criteria jsonb NOT NULL DEFAULT '[]',
  proof_line          text,
  github_url          text,
  linkedin_published  boolean NOT NULL DEFAULT false,
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now()
);
```

With RLS (`auth.uid() = user_id`), indexes on `user_id` and `created_at DESC`, and an `updated_at` trigger.

**Session save:** Server-side insert in `close-session/route.ts` after Claude response. Calls `revalidatePath('/proof')` after successful insert.

**Each row displays:**
- `session_date` (human-readable: "May 30")
- `week_topic`
- `proof_line` — if set, show text; if null, inline `<input>` placeholder "Add your proof line" that saves on blur via PATCH
- `github_url` — if set, show as link; if null, inline `<input>` placeholder "Add GitHub link" that saves on blur via PATCH
- `linkedin_published` — checkbox; when checked, green left border; optimistic update (roll back on PATCH failure)

**Streak counter (cherry-pick accepted):** Consecutive sessions with `linkedin_published = true`, computed client-side from rows. Shown at top: "4-session streak".

**No modal, no separate form.** All editing inline.

**Empty state:** "No sessions yet. Complete a tutor session to start your proof trail."

**API routes:**
- `GET /api/proof` — sessions for current user
- `PATCH /api/proof/[id]` — updates proof_line, github_url, or linkedin_published (separate file: `src/app/api/proof/[id]/route.ts`)

**Technical acceptance criterion:** `/proof` renders last 10 sessions under 500ms. New session appears after close-session + navigation to /proof.

## Build Step 3: Daily Topic Prompt (~1h)

**20 topics (frontier lab prep sequence):**
1. Transformers: attention mechanism and positional encoding
2. Training dynamics: loss curves, learning rate schedules, gradient clipping
3. Tokenization: BPE, SentencePiece, vocabulary tradeoffs
4. Fine-tuning: LoRA, QLoRA, full fine-tune tradeoffs
5. RAG: chunking, retrieval, reranking
6. Evaluation: BLEU, ROUGE, LLM-as-judge, human eval design
7. RLHF: reward modeling, PPO, DPO
8. Inference optimization: KV cache, quantization, speculative decoding
9. Agents: ReAct, tool use, multi-step planning
10. Memory architectures: context window, external memory, retrieval
11. Multimodal: vision encoders, cross-attention, CLIP
12. Distributed training: data parallelism, model parallelism, ZeRO
13. Prompt engineering: chain-of-thought, few-shot, system prompt design
14. Safety and alignment: RLHF limits, Constitutional AI, red-teaming
15. Interpretability: attention visualization, probing, circuits
16. Embeddings: similarity search, FAISS, dense vs sparse retrieval
17. LLM architecture variants: Mamba, mixture-of-experts, sparse attention
18. Research reading: how to read a paper in 30 minutes (meta-skill)
19. Contribution: how to write a research note / blog post from a project
20. Portfolio: how frontier lab recruiters evaluate GitHub and LinkedIn

**Mechanism:** `sessionCount = SELECT COUNT(*) FROM tutor_sessions WHERE user_id = $1` in the tutor page server component. Current topic = `sessionCount % 20`. Pass as SSR prop — no client-side fetch.

**Display:** "Today: [topic]. Suggested based on your progress."

**Technical acceptance criterion:** Topic appears within 100ms (SSR prop). No network call. Default to topic 1 if session count unavailable.
